Updated: 31 October 2026.

Roster imports now run as persistent background jobs in PostgreSQL. The existing Admin roster screens show account progress separately from email progress. Closing or refreshing the browser does not cancel the server job; restarting the backend resumes pending rows. Graceful shutdown stops claiming new work and lets current work finish. A database transaction protects each account, queued onboarding message and saved result together.

**File safeguards:** SheetJS is pinned to the publisher’s supported 0.20.3 distribution, replacing the vulnerable npm-registry 0.18.5 release. Files are parsed in a browser worker with a 10-second timeout. Limits are 2 MB per file, 2,000 data rows, 32 columns and 500 characters per cell. ZIP archive size checks reject workbooks advertising more than 20 MB of expanded content. Formulas and unsafe/duplicate headers are rejected. Both the browser and server validate the required identity, name, email and role-specific fields. No student ID, name, email or phone number is invented to complete a missing row. Specimen templates now contain blank cells instead of example people and reusable passwords.

**Account behavior:** new accounts receive a generated password unless a valid 12–128-character initial password was supplied. Existing accounts have their profile fields updated and keep their password, even if an initial-password column was supplied again. Re-importing a roster does not resend onboarding credentials for an existing account. Unknown assigned Mentor IDs and conflicting RO category assignments are reported as failed rows. Import Mentors before students who reference their IDs. Row results identify created/updated/failed records; password downloads contain initial passwords only for accounts created by that job.

**11 November password-download fix:** the Student, Mentor and RO directory buttons now fetch the latest completed import results through the authenticated Admin API. Their CSV contains initial passwords only for accounts created by that import; it never substitutes `N/A` from the public account list. A queued import shows a wait message, and an import that only updated existing accounts shows that no new passwords can be retrieved. The RO directory now has the same download button. Each recent import card also downloads its own results, with the action disabled until processing finishes. Browser tests verified actual CSV downloads for all three roles using synthetic credentials; no real passwords were printed or changed.

**Progress and recovery:** submitting a valid roster returns an import ID promptly. The backend processes accounts independently of the original web request and saves completed rows. Repeating the same request key does not duplicate the job. Account locks and row claiming coordinate workers through PostgreSQL. Recent jobs remain visible in the existing Student, Mentor and RO tabs; results and private credentials can be downloaded there. Downloaded CSV cells are escaped to prevent spreadsheet formulas from executing. The email-only retry button does not recreate users or reset passwords.

**Email queue:** automatic notices, onboarding messages and custom Admin messages are saved before background SMTP delivery. The default limits are 10 attempts per rolling minute and 400 attempts per rolling 24 hours per configured sending account. These are application settings, not a provider allowance or guarantee. Set `EMAIL_MAX_PER_MINUTE` and `EMAIL_MAX_PER_24_HOURS` only after IT confirms the real sender quota. Other applications using the same mailbox also consume provider allowance, so a dedicated institutional sender is preferable. At the default daily setting, onboarding 1,000 students needs multiple days; account creation does not wait for those emails. Ticket notices are preferred ahead of bulk onboarding messages when claiming work.

Configured limits survive process restarts and include recorded attempts. Explicit transient SMTP failures receive bounded background retries. Provider quota responses pause the sending account, and authentication failures also trigger a pause. A message whose delivery is uncertain after a crash is marked unconfirmed and is not automatically resent; check provider logs first. Eligible failed/disabled/unconfigured onboarding messages can be requeued from the import card after configuration is corrected. Missing, invalid or reserved addresses do not fall back to a developer inbox. Recipient address/assignment/password changes cancel stale queued credentials or notices instead of delivering to the old account. Credential retries must use the original matching account state; re-importing an existing account intentionally preserves its password.

`DISABLE_EMAIL=1` prevents actual delivery. It remains active in the running development verification session. The user’s existing developer account addresses are unchanged and remain eligible in development mode. Final institutional-address cleanup is still deferred at the user’s request. `NODE_ENV=production` blocks the known legacy developer inboxes and requires a public HTTPS `APP_URL`.

**Encryption and access:** job input/results and queued mail payloads are authenticated-encrypted in the database. Account passwords remain salted scrypt hashes; onboarding audit bodies omit the initial password. Private queue tables deny public database access. Only authenticated Admins can submit rosters, read job credentials or request onboarding retries. Ordinary state responses and table gateways do not expose encrypted payload columns.

Development generates `.local/queue-encryption.key`, excluded from Git. Production requires `QUEUE_ENCRYPTION_KEY`, a private base64-encoded 32-byte key. Back it up separately and retain it when moving/restoring that database. A stored fingerprint prevents startup with a different key. Losing it prevents recovery of existing encrypted pending jobs; do not replace the fingerprint to bypass that check. Temporary credential/result retention must be agreed with the institution before launch; automatic deletion of the current development history has not been introduced.

**Validation and limits:** tests queue 1,000 synthetic records, parse a real 1,000-row workbook in the browser, process representative account jobs in an isolated database schema, resume a worker, preserve an existing password, exercise retries and quota deferral, cancel stale mail, and restore progress after a browser refresh. SMTP in these tests is fake. This is not a complete 1,000-real-email delivery test, a measured production throughput benchmark, or a 1,500-concurrent-student load test. Other release blockers in `docs/LAUNCH_READINESS.md` still apply.

Dependency updates also address the newly reported Express/body-parser, build-tool and mailer advisories. The old inbox client’s semver dependency is pinned to compatible patched 5.7.2 through an override; its encoding path is regression-tested. A clean `npm audit` report is one check, not proof of complete application security.
