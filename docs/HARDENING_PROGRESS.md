**Reminder requested for launch:** before deploying or going live, remind the user to provision individual accounts for approximately 10 professors (Principal, HODs and Dean) using `npm run admin:add` on the production database. They all use the existing Admin dashboard and permissions. See `docs/FOLLOW_UPS.md`; this setup is still pending.

**Step 1: login and private data access — implemented and applied locally.**

Previously, someone could request dashboard data without logging in. The server now checks a real login session before returning protected data or accepting changes. Choosing “Admin” in the browser does not grant Admin access. Students receive their own tickets; mentors receive assigned students; ROs receive assigned issues. Administrative operations require an Admin session.

Existing student, mentor and RO passwords were converted to salted scrypt hashes. A hash lets the server check a password without storing the original password. All 21 students, 10 mentors and 12 ROs were preserved. There were no grievances, meetings or recordings at the time of migration; their counts remain unchanged. Migration runs inside a transaction, so a failure rolls back its database changes.

**Student enrollment:** new student accounts are created through Admin roster import only. Public signup is removed and its endpoint returns HTTP 403. Existing accounts keep working. New passwords supplied in roster imports must contain 12–128 characters; blank password cells receive a random generated password. Login links contain an ID and role, never a password.

**Admin login:** select Admin, use ID `ADMIN`, and obtain the initial password from the private file `.local/admin-bootstrap.json`. Open that file locally; do not paste it into chat, email, screenshots or Git. It is excluded from Git. After login, use **Change password**. This replaces the initial password and signs out existing sessions on all devices. The bootstrap file is an initial credential record, not a password-recovery mechanism: its old password stops working after a change.

**Adding professors as Admins:** open the project terminal and run `npm run admin:add`. Enter a unique account ID (for example `ADMIN-PRINCIPAL` or `ADMIN-HOD-CSE`), the professor’s full name and their institutional email when prompted. The command creates one account and prints the location of its private initial-credentials JSON file under `.local/`. Share that account’s initial password privately with its owner. They select **Admin** on the existing login page and use their own ID or email and password, then select **Change password** after signing in. Repeat the command for each professor. All these accounts have the same Admin dashboard and permissions; no additional modules are introduced. Existing IDs/emails are rejected instead of overwriting an account. The command does not send email or create sample accounts. It uses the existing application database connection; start the app once to initialize its tables before adding accounts.

Sessions are stored in PostgreSQL and expire after eight hours. The browser holds the session in an HttpOnly cookie; production cookies require HTTPS. State-changing requests also require a session-bound security token. Logout revokes the session on the server. Protected API responses are marked not to be cached. Old browser caches containing account lists, tickets or login identities are cleared; private account data is no longer saved there. Login attempts are limited per account in the current process; a shared/distributed limiter is still needed before multiple API instances or unrestricted public use.

Direct browser database access is closed. Application tables have row-level security enabled, the old public policies are removed, and the Supabase `anon`/`authenticated` roles have no application-table privileges. Browser data operations now go through the authenticated Node API. The Node database connection must use a protected backend database role with the necessary privileges, never a browser publishable key.

The old password bypasses and the HTTP database-reset route are removed. Vite now proxies the real backend instead of providing a second set of development APIs. Database and mail passwords are loaded from private environment settings; embedded credential defaults have been removed. **Previously committed credentials still require rotation in the provider accounts. Removing source defaults does not revoke exposed credentials.**

**Validation:** the complete regression suite passed 147 tests, with three opt-in database checks skipped in that run. The security database integration check was also run separately and passed: it creates an isolated schema, tests password preservation, private queries, password changes and session revocation, then rolls back. Real browser verification passed Admin login, session restoration after refresh, the password dialog, logout, absence of private local-storage caches, and record-count preservation. Browser recording tests confirmed that recorded media still saves and plays. The production build passed. An additional live read-only audit confirmed anonymous dashboard HTTP 401, no public-all policies and no anonymous application-table privileges. Test fixtures did not email users or modify existing grievances.

The login browser check also found and fixed a layout shift that could swallow the first click on Sign In when the password hint disappeared.

**Running locally:** configure `server/.env` using `server/.env.example`, then run `npm run dev` and open `http://localhost:5173`. The currently running verification session has email disabled through the process setting `DISABLE_EMAIL=1`; that setting does not change your saved environment file. Keep test email disabled until recipient routing is corrected. Restarting normally uses your saved environment settings. The build alone does not deploy a public server.
